# Astrology provider decision record

Researched November 2, 2026 using provider documentation, current pricing pages, and published licenses. **Decision reopened: live daily, weekly and monthly horoscopes remain required. No recurring subscription is authorized. No provider has been selected, subscribed to, or called with credentials. Public sign-only requests were made; no birth data was transmitted.** Prices below are published prices, not purchase quotes; taxes and future changes are additional. Live reliability and entitled account coverage still need credentialed contract tests.

## Recommendation

Keep content and calculation services separate. Recommend **Astronomy Engine for local calculations**, with a tested tropical/Whole Sign adapter and local GeoNames/IANA birthplace resolution. It has no recurring service charge and can keep birth details inside Muse.

For written forecasts, prioritize **FreeHoroscopeAPI as the conditional no-cost candidate**, subject to the live-response and rights blockers below. Its current terms explicitly allow commercial applications with attribution; the earlier conclusion that commercial permission was unverified is superseded. It is **not ready for activation**: the live weekly feed returned the previous week's date and stale edge responses. Cache/archive rights, publication timezone and rollover behavior still need clarification.

The earlier $49/month DivineAPI recommendation is retained below only as historical comparative research. It is outside the user's current no-subscription constraint. The earlier instruction to continue independent local work was temporary sequencing, **not permanent deferral or removal of horoscopes**. No provider adapter is being integrated before this review.

### Actual-response protocol and limits

Used unauthenticated HTTPS GET requests to the documented FreeHoroscopeAPI routes, one request at a time, for each sign and period. Captured status, date/period/sign, word count, latency, selected cache metadata and SHA-256 reading fingerprints. Full reading text stays out of repository evidence. Requests send only the public sign; no user identifier, cookies, birth details, birthplace, coordinates or journal text. See `content/astrology/horoscope-provider-probe.json` for observations. These are investigative calls, not a runtime integration or a contractual load/uptime test.

Coverage pass: **36/36 HTTP 200 with matching sign/period and nonempty text; 36 distinct reading fingerprints**. This is structural coverage, not freshness approval.

Observed on November 2 in America/Los_Angeles, shortly after November 3 00:00 UTC. The provider's UTC HTTP Date header is distinguished from Muse's local date. November 2 is Monday. Daily samples included both November 2 and November 3 dates without a timezone field. Weekly responses labeled October 26 and `cf-cache-status: STALE` are not safe to present as November 2–8. The exact intended week convention remains undocumented; the date mismatch and stale headers require resolution rather than silently relabeling content. Aries weekly revalidation using `Cache-Control: no-cache` again returned October 26 with the identical reading fingerprint and stale header. Many weekly requests took roughly ten seconds, versus subsecond cached daily responses.

Content review: actual prose is readable, sign-specific general guidance, with longer weekly/monthly paragraphs. The inspected Aries periods repeat themes of busyness, prioritization and perseverance. There is no structured evidence of separate Love, Career, Money, Creativity, Social or Wellbeing forecasts. Similar wording does not establish how the text was authored, whether it is licensed from an upstream source, or whether it is recycled; provenance remains unverified. Do not label it human-authored or astrologically personalized. Response fields are only `date`, `period`, `sign`, `horoscope`.

Missing/invalid sign requests both returned the documented HTTP 400 codes (`missing_sign`, `invalid_sign`). The payloads include no explicit sample flag; absence of that flag does not prove freshness. A short audit cannot prove reliable future daily/weekly/monthly changes or uptime. Repeated same-period hashes test stability only. The stale weekly feed already fails the requested freshness expectation. Longitudinal rollover checks remain required after the publication schedule is clarified; they must compare provider dates and text fingerprints across actual daily/weekly/monthly boundaries. Do not invent historical date parameters to simulate that evidence.

### Integration design once blockers are resolved (planned, not activated)

- One server-only provider adapter behind `lib/astrology/forecast.ts` serves both Daily Edit and Observatory. Continue using the existing canonical zodiac preference; temporary browsing never changes it. Daily Edit keeps its existing position and daily scope; Observatory adds the three verified periods.
- Expose only **Overview** for FreeHoroscopeAPI. Other life areas remain unavailable until distinct provider text is verified; general paragraphs must not be split or relabeled to manufacture categories.
- Send only sign. User timezone remains inside Muse for civil dates/UI; preserve the provider's actual period identity and timezone separately once known. A rollover mismatch produces a dated/unavailable state, never a newly labeled old reading. The normalized contract currently assumes a known civil range, so an adapter cannot honestly fill it until the weekly/publication conventions are resolved.
- Central bounded cache and request coalescing prevent one upstream call per reader. Use provider-authorized TTL, timeout, limited backoff and 429 handling; existing eight-second deadline would currently time out slow weekly responses. Do not raise it blindly to mask stale upstream results. Test on Vercel before enabling either surface.
- Render normal Muse UI with source attribution, not a third-party iframe. Do not send user IPs/birth details through browser calls; server requests share only non-personal public sign content. Commercial app permission appears compatible with authenticated web/PWA, but permanent snapshots, offline/service-worker storage and redistribution/export of saved text remain distinct unresolved rights.
- Until written retention rights are clear, planned journal saves may retain user-authored notes and source/date/sign references, **not copied forecast text**. Do not claim a past reading can be reopened when the provider offers only current readings. Do not put full readings into PWA caches by default.

### Concrete blockers to clear before activation

1. **Freshness:** provider resolves the stale October 26 weekly feed and explains publication timezone, daily rollover and weekly/monthly labels; rerun all 36 cases and genuine boundary checks. Date validity and HTTP 200 alone are insufficient.
2. **Rights:** confirm upstream content provenance/authority, shared server cache TTL, private saved-reading retention/export, PWA/offline storage and deletion obligations. Current commercial-use permission is affirmative; these additional rights are unspecified, not an asserted ban.
3. **Operations:** establish REST request/month and per-minute limits, acceptable shared caching, outage/rate-limit behavior and support expectations. A no-key service is not automatically unlimited or guaranteed.

## Adapter requirements, regardless of vendor

- A capability matrix must specify real categories **per period**, all supported signs, timezone/date conventions, cache policy and license-permitted retention.
- Normalized data must identify provider, sign, category, period, inclusive civil-date range, headline/preview/full text, source, retrieval time, expiry and availability. A cache key must include provider/version, sign, category, period/range, request timezone or effective offset, and language where relevant.
- Dedupe concurrent requests. Reject mismatched dates/signs, invalid/sample responses and absent attribution. Support bounded timeouts, 429/retry-after, provider outages and explicit stale status only when license policy permits it. Do not assume local midnight is every provider's publication schedule.
- Persistent provider cache is non-personal service data. Journal snapshots are separate private user records with their own retention policy. Personal notes must survive provider-content removal where appropriate.
- Both surfaces must call the same service and display the same request identity/content. Temporary browsing never mutates the canonical default zodiac preference.
- Secrets are server-only environment variables. Historical paid-option research only (outside current no-subscription scope): if DivineAPI were approved, proposed names were `ASTROLOGY_CONTENT_PROVIDER=divineapi`, `DIVINE_API_KEY`, and `DIVINE_AUTH_TOKEN`; these are **not configured or used yet**. Calculation/GeoNames/IANA recommendation requires no external birth-data API credential.
