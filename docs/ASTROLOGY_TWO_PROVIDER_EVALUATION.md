# Cosmic Observatory — two-provider research and natal-wheel recommendation

**Status: research recommendation, not an approved integration.** Checked November 2, 2026 in America/Los_Angeles. The Observatory's six-section local implementation and QA were completed first; see [implementation report](COSMIC_OBSERVATORY_IMPLEMENTATION.md). No provider adapter, chart renderer, birth profile, Tarot engine, database or hosted environment was changed by this evaluation. All live calculations used synthetic reference cases. “Verified” below distinguishes an actual response from a statement in provider documentation.

## Actual synthetic natal calculation comparison

All five cases used exact, invented place/time combinations. Muse resolved each civil time through its IANA rules, then supplied **only the UTC instant** to FreeHoroscopeAPI with `zodiac=tropical`; no place, user birth profile or account identity was transmitted. Both outputs describe geocentric apparent ecliptic longitude of date. Muse uses Astronomy Engine 2.1.19; FreeHoroscopeAPI reports Skyfield 1.55/JPL DE421 and outer-planet barycenter targets. Angular differences use shortest distance on a 360° circle. Complete 50-body values, signs, retrograde flags and local angles/cusps: [synthetic comparison data](../content/astrology/provider-calculation-probe.json).

| Synthetic case | Resolved UTC | Largest difference among 10 bodies | Sun / Moon difference | ASC/MC comparison |
| --- | --- | ---: | ---: | --- |
| Greenwich, 2000-01-01 12:00 UTC | 2000-01-01 12:00Z | 0.185′ | 0.011′ / 0.005′ | Muse computed; provider does not expose angles. |
| Paris, 1950-06-15 12:00 local | 1950-06-15 11:00Z | 0.119′ | 0.011′ / 0.096′ | Muse only. |
| Los Angeles, 2024-03-10 01:30 local (before DST jump) | 2024-03-10 09:30Z | 0.189′ | 0.009′ / 0.043′ | Muse only. |
| Buenos Aires, 2019-07-20 10:10 local | 2019-07-20 13:10Z | 0.248′ | 0.003′ / 0.006′ | Muse only. |
| Kolkata, 2001-01-01 12:00 local (+05:30) | 2001-01-01 06:30Z | 0.182′ | 0.011′ / 0.024′ | Muse only. |

**Verified live:** 50/50 positions had the same tropical sign and retrograde flag; median difference was 0.024′ and maximum 0.248′. These small differences are consistent with different ephemeris/target conventions and are not evidence of a natal-chart error. This cross-check does **not** validate Muse angles/houses/aspects against FreeHoroscopeAPI, which does not return them. The existing independent northern/southern angle fixtures and JPL position fixtures remain the actual local validation. FreeAstrologyAPI returned no calculation data without a key, so **no numeric three-way comparison or inference about its accuracy is possible**.

Muse's test suite verifies a Los Angeles spring DST gap returns no candidate, the fall fold returns two, Kolkata +05:30, and a Paris 1880 offset with seconds. FreeHoroscopeAPI positions start in 1900, so they cannot check that 1880 case. FreeAstrologyAPI's timezone endpoint documents an IANA offset/DST lookup, while its calculation endpoints require the caller to pass the correct numeric offset and its FAQ says they do not apply DST automatically. Ambiguous folds, nonexistent times, historical tzdb version, older political boundaries and geographic disambiguation were **not tested** against that provider. [Timezone endpoint](https://freeastrologyapi.com/api-reference/time-zone/timezone-with-dst), [geo lookup](https://freeastrologyapi.com/api-reference/geo-location/geo-details), [FAQ](https://freeastrologyapi.com/faq).

## Calendar, tarot and SVG assessment

- **Calendar — verified live:** the FreeHoroscopeAPI `/times` request for synthetic Greenwich coordinates on March 10, 2024 returned `Europe/London`, sun-event and moon-event/phase fields. This is a daily local sky utility, not evidence for future ingresses, retrograde stations or major transits. Panchang follows a sunrise-based Vedic day with approximate Lahiri conventions and should not be silently mixed into Muse's Western tropical calendar. Muse already calculates lunar phases and seasons locally without requests. [Times/Panchang docs](https://freehoroscopeapi.com/docs), [sample metadata](../content/astrology/provider-utility-probe.json).
- **Tarot — verified live:** 78 unique cards include `meaning_up`, `meaning_rev` and `desc`. Median lengths measured 18, 7 and 41 words; some reversed meanings are only three words. A deck endpoint is meaningful as an external comparison/reference only, not a reason to replace Muse's original 78-card Grimoire, ritual choices, reading history or local random draw. No external tarot content was copied into the app. [OpenAPI](https://freehoroscopeapi.com/openapi.json), [sample metadata](../content/astrology/provider-utility-probe.json).
- **SVG — verified documentation, not live output:** FreeAstrologyAPI's Western wheel returns an S3 SVG **URL** rather than a structured interactive chart. The separate Vedic SVG-code example contains an external font import and embedded name/date/location fields; it shows why untrusted inline SVG would need sanitization, but it is not proof the Western wheel contains the same markup. Unknown URL expiry/public access and third-party image requests are further privacy and offline concerns. Never inject provider SVG into DOM unsanitized or let it carry private details in a public URL. An `<img>` isolates script but still gives up interactive planet targets and token-level styling. Muse's local SVG is the better owned renderer. [Western wheel](https://freeastrologyapi.com/api-reference/western-astrology/natal-wheel-chart), [Vedic SVG example](https://freeastrologyapi.com/api-reference/horoscope-chart-svg-code).

## Proposed interactive-chart UX architecture — no change made

Use option **B: Muse-owned SVG from the persisted local chart**. The current component already renders a circular wheel, zodiac/house divisions, true-longitude leader lines, aspect lines, ASC/MC, ten keyboard/touch-selectable planets, adjacent complete text list and theme-aware colors. Keep chart identity and selection in the Observatory, with a single focused detail surface showing computed sign/degree/house/retrograde/aspects alongside complete original planet, sign, house and aspect interpretation. That surface should link to related library entries, connected chart placements and a prelinked journal editor; closing it should restore wheel focus and selection. House/angle/aspect targets can use the same detail pattern after focused accessibility testing. Avoid extra “read full interpretation” hops. Preserve SVG text alternatives, numeric contrast checks, responsive layout, Muse Quiet and reduced-motion behavior. Do not replace or extend the wheel during this research-only task.

A provider SVG overlay (A) would require synchronizing unknown remote geometry, colors and text targets to Muse's saved chart and would still transmit private birth data. Hybrid provider calculations plus Muse SVG (C) could be a future diagnostic, but has no demonstrated accuracy, privacy, cost or resilience advantage today. Local data and rendering require **zero provider calls** per chart visit; saved charts and journal notes stay available during provider outages. Client-side interaction remains within Muse's authenticated owner boundary.

| Workflow, if someday approved | Expected external calls before caching | Caching/fallback rule |
| --- | ---: | --- |
| Open existing chart; explore placements/library; save journal; browse local calendar | **0** | Existing private chart/journal and local calculations remain usable offline where Muse itself permits; do not depend on external SVG. |
| Fetch one sign/period written forecast | **1** FreeHoroscopeAPI request per uncached sign/period | Share a server-side normalized service with Daily Edit, but set date/TTL only from documented refresh boundaries and rights. Reject mismatched/stale content; never label last week as current. Save user notes/reference only until snapshot/export rights are confirmed. |
| Optional provider sun/moon times for one explicitly chosen location/date | **1** FreeHoroscopeAPI request | Send only consented coordinates, retain only permitted data, label source/timezone, and fall back to local supported events if unavailable. |
| Optional FreeAstrologyAPI diagnostic natal validation | About **3** calls for planets/houses/aspects; add **1** for SVG, **1** timezone, **1** geocoder as needed | Not part of current workflow. Calls are keyed, nominally one credit each per docs and rate-limited to one/second on free tier. Cache only if written rights allow; never send a real profile without separate approval and disclosure. |

## Gates before any integration

1. **FreeHoroscopeAPI:** resolve stale weekly publication, date/timezone boundaries, measured rollover behavior, REST quota/SLA, content provenance, cache TTL, PWA/authenticated use and private text-save/export/offline rights. The prepared [inquiry](FREEHOROSCOPEAPI_INQUIRY.md) remains **unsent**. No specialized life-area categories have been verified.
2. **FreeAstrologyAPI:** confirm free-tier commercial production entitlement despite conflicting site wording, actual account quota/endpoint credits, caching/reuse, chart-URL privacy/expiry, birth-request logging/deletion, historical zone behavior and a matching synthetic test suite with a legitimate key. Obtain explicit approval before any external real-birth-data flow; no account was created in this evaluation.
3. **Muse UX decision:** preserve the local engine and SVG; prioritize a focused interaction refinement only after review of this architecture. No dependency, provider adapter, chart renderer, Tarot content or hosted data was changed here.
