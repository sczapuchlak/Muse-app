# Book story #135 — Phase 0 audit and proposed plan

Status: **audit approved by Stephanie on 2026-11-09; implementation in progress on the local feature branch.** This document records the original audit and proposed plan. The approved behavior and implementation status are in `PRODUCT_RULES.md` and `FEATURE_SPEC.md`.

## 1. Current architecture and functionality

**Ownership and cohesion check.** Collections → Books is the navigation home. `whimsy_books` owns one canonical book and its optional edition metadata, position, status and read completions; `whimsy_reading_sessions` owns dated sessions; `whimsy_reading_timers` owns the one open timer per user. `collection_series` and `collection_series_members` own optional series order, role and release state. `collection_curated` owns user collections. Reading Atlas, Insights, the Reading Desk, Daily Edit and the decorative shelf project these same records. Any journal entry added for a book should point to its book ID, optionally read and session IDs, and retain a book-title snapshot for deletion/history semantics. Nothing here requires a series, timer, journal or decorative shelf placement. Reading begins in the Library/Reading Desk, can lead to session capture and reflection, and appears later in Atlas/Insights. The existing Muse modal, segmented navigation, choice menu, cover component, material tokens and reduced-motion patterns are the starting points. A new journal owner or schema must be decided before implementation; it is not silently assigned to Mindspace Notes.

## 3. Book detail UX proposal

Use the existing `/collections?view=books&book=…` deep link and canonical record. On desktop, present a bounded, responsive detail sheet/page with a cover-led left area and title, author, status, primary action, progress and series summary beside it. On phones, show the cover and title quickly, then the primary reading action within the first screen, respecting safe areas and bottom navigation. Follow with a compact Overview and a segmented content selector for Sessions, Journal, History and Edition where content exists; keep labels subject to visual review. The existing editor remains the write path for book metadata and prior reads. Keep the long session list from becoming the modal's default content. Show dates, current/total pages and percent only when known; indicate unknown length plainly. Reuse the cover fallback and display typography, existing glass/material tokens, visible focus, touch targets and reduced-motion behavior. Do not change the global theme.

## 4. Cover atmosphere recommendation

Start with CSS composition using a small set of sanitized palette values, restrained gradient blooms and a solid token-backed reading surface. Try a one-time client pixel sample from the selected HTTPS cover using a CORS-enabled image; cache a palette by cover URL in memory (and optionally in browser storage only after privacy/performance review). Sample and clamp luminance/chroma, reject near-neutral/noisy or low-contrast results, and fall back to curated theme-aware palettes. Browser extraction is cheap for a small downscaled canvas but a cross-origin image without permissive CORS taints the canvas. Therefore a cover must remain fully usable without sampling. If real-world cover hosts make extraction too unreliable, evaluate a constrained server-side palette service for trusted provider hosts; arbitrary URL fetching needs SSRF, size, content-type and timeout defenses, so it is a later technical decision, not an assumed requirement. No new paid service or full-resolution image copy is proposed. Avoid animation that repaints the whole screen. An atmosphere-off preference is reasonable to offer in the detail UI if testing shows readability or comfort problems; it should be local to this treatment and not alter the saved global theme.

## 5. Reading action and status plan

Expose **Start/Continue reading**, **Resume session**, **View history** or **Read again** according to book/timer/read status, all calling the existing `timerAction`, `moveBook` and read-cycle helpers. A planned book started from detail should first move to reading, then start the timer, with an idempotent command/revision strategy. Record the pre-start status and revision in the pending timer context so discard can restore it only if no later independent status change or session save has occurred; a failed timer start must not leave a misleading status change. Finished books begin a new read through `shelfMove`, preserving completions. Do not force a planned book's status merely because its detail was opened.

Replace the active timer's browser confirmation with existing `MuseModal`: **Close this chapter?**; the issue's exact loss message; primary **Keep reading**, secondary destructive **Discard session**. The modal must leave the timer running/paused while open, preserve recovery on navigation/refresh and discard only after server acknowledgement. A failed/offline discard stays visibly pending, never claims the session was deleted. Restore an automatically changed status only under the conditions above. Saved sessions, pages and notes stay untouched.

## 6. Series strategy

Use `seriesProgress` unchanged as the calculation authority and render a concise summary beside book progress: series title, decimal number, released/known scope and completed count, plus current/remaining and next released unread where computable. Link to the existing Series detail. Preserve companion/novella role, fractional order, multiple series memberships and announced/unknown release semantics. A blank gap is unknown, not an imported title. The current series editor lets users correct order, role and release state. Add missing installments through the current create/search book flow, then attach them to that series. Any provider-derived series suggestion would require provenance and user confirmation; current providers do not supply reliable series data.

## 7. Journal and history strategy

Propose one **book journal entry** model with a required kind (`quote` or `thought`), body, date, optional page/location/chapter, optional personal note for quotes, optional read/session references, and stable book ID plus title snapshot. This is new canonical content owned by Books; it does not copy Mindspace Notes. The relationship to a read/session is optional; deleting or correcting a session must not delete writing. Existing session notes, reviews and Mindspace notes retain their meaning and storage. A book detail journal can show these as clearly labeled linked sources only if users benefit; edits go to their original owner. Search and chronological ordering should cover journal entries, while book-level search of note text is an explicit performance/privacy choice.

Read history should use `bookReads` and `readStats` with per-read dates, opinions and sessions. Keep unlinked legacy sessions in their own section with assignment controls. Imported historical reads can later be represented as completions with no fabricated timer data; no CSV import belongs to this story. Distinguish completed reads from unique titles and session counts.

## 8. Analytics and browsing plan

Book detail first shows four or fewer real metrics: active time, logged pages, sessions and pace where there is sufficient joint data. An expanded Sessions/Statistics view can show daily time/pages, a progress timeline based only on dated saved positions, and useful 7/14/30/all ranges when data supports them. Reuse `reading-stats.ts` and Atlas calculation rules rather than storing totals. Manual session minutes and timed minutes retain their source labels. Empty and unknown values are explicit.

Collections Overview already has Board and Library; Bookshelf has cover grid, so retain both. Add a compact row/list presentation within the same canonical Books browsing surface only if usability testing supports it, remembering its preference alongside existing Collections mode. Extend title/author/genre/series/status search and combinable filters; books have no canonical tags today, so a tag filter must not pretend book tags exist. Add meaningful sort orders using existing timestamps/read dates, with stable ties. Ensure the full library remains reachable from every overview mode.

`readWhimsy` pages network reads but materializes all records for complete analytics; `readCollections` selects entire tables; both UI grids map all matched books and cover images at once. For 400–1,000 books, first profile query cost and browser render on desktop/phone. A safe first step is incremental visible batches and lazy cover loading with width/height, preserving the full in-memory dataset for filter/sort and analytics. Consider server pagination or virtualization only if measurements show the first step is insufficient; those need separate handling for complete statistics and cross-record filters. Memoize derived search keys and avoid repeated session scans inside comparators. Avoid an image optimizer for arbitrary user HTTPS URLs without a provider policy.

## 9. Schema, risks and proposed phases

**Schema:** Detail, atmosphere, timer surfacing, series summaries, read analytics and library controls can use existing records. The journal likely needs an owner-scoped `book_journal_entries` table or a carefully justified equivalent; audit the account export/delete paths, RLS policies, foreign-key deletion behavior and staging migration before approving that part. Cover palette storage is not required. Status rollback context may need a small optional timer-payload field, with validation of existing timer immutability rules; no table change is presumed until the command path is designed.

**Risks:** cross-origin cover sampling; low-contrast atmospheres in light-card themes; timer/status races across devices; old sessions without read IDs; series totals that only reflect saved books; large cover grids and broad reads; journal deletion or privacy semantics; and mobile modal/safe-area behavior. Do not imply provider series completeness or infer missing pages/time. Existing uncommitted files in the worktree are unrelated and were not changed.

**Proposed sequence and review gates:**

1. Detail visual foundation and accessible cover atmosphere, with desktop/phone review in every theme/material.
2. Direct reading actions, planned-status transition, cancellation dialog and rollback, with two-device/offline/recovery tests before visual signoff.
3. Series summary, book-level statistics/history layout, then journal schema and capture after its data contract is approved.
4. Library search/filter/sort and measured scale work; test with 10, 400 and 1,000 books on phone and desktop.
5. Optional book card export as a separate enhancement after preview/privacy decisions.

**Acceptance/testing strategy:** Preserve IDs, editions, sessions, completions, reviews, positions, Collections memberships, Atlas/Insights totals and decorative shelf placement. Run focused reading-cycle, timer, series, lookup, Atlas and Collections tests plus local two-device database checks. Test planned start → cancel, finished reread, offline command retry, overlong recovery, saved-versus-unlinked sessions, partial series metadata and missing page totals. Then lint, typecheck, production build and actual mobile/desktop visual QA (keyboard, screen reader labels, contrast, reduced motion, safe areas and large libraries). Database changes go to local/staging first under `DATABASE_RELEASES.md`; production requires explicit approval.

**Decision requested:** Approve or amend this audit and the phased scope before any feature implementation, as required by issue #135. In particular, decide whether the proposed Books-owned quote/thought journal and its migration belong in Phase 3, and whether book-card export remains a separate enhancement.
